## 현재 상태

2026-09-22 12:39 KST부터 사용자의 약 2시간 연속 작업 요청을 받아 후속 작업을 진행했다.
이 문서는 중간/누적 결과이며 **2시간 경과 또는 실주행·학습 완료를 뜻하지 않는다**.
다른 테스트의 사용 범위가 확인되지 않아 CARLA/학습 실행은 하지 않았다. 원격은 개인 dataset
폴더 존재와 GPU 0 상태를 읽기 전용 조회했을 뿐이다. 조회 시 GPU 0은 0MiB·0%였지만 미래
점유가 없다는 보장은 아니므로 작업을 제출하지 않았다.

로컬 작업은 단일 프로세스·낮은 우선순위의 CPU 진단과 별도 새 파일에 한정했다. 공용 수집기,
실행 launcher, runtime gate, 모델, 학습 데이터는 변경하지 않았다. 원본 실패 기록도 보존했다.

## 1. 실제 급제동 위치를 구분했다

| 원본 | native 20Hz의 감속 한계 위반 구간 | camera 10Hz 위반 구간 | 관측된 위치 |
| --- | ---: | ---: | --- |
| Town01 M06 | 10 | 6 | 주행 중간 5개 + tail 전환 5개 (20Hz 기준) |
| Town07 M05 | 2 | 2 | 종점 접근/정지 |

Town01 주행 중간은 brake 0.5, tail은 brake 1.0이 관측됐다. Town07은 brake 0.15에서도
순간 감속 한계를 초과했다. 이는 명령과 측정의 동시 관측이며 독립적인 인과 실험은 아니다.
신호등 상태와 stop-line 거리 로그가 없으므로 중간 급제동을 신호 원인이라고 확정하지 않았다.
순간 native 최소 속도 변화율은 각각 −25.3873, −16.5064m/s²이며 주행 전체 평균이 아니다.

## 2. 별도 속도 참조와 비활성 연동 경계를 구현했다

- `research_speed_reference.py`: 곡률 속도 계획에 현재 위치/속도, 정지 거리, 긴급 상태를 결합.
- 미리 계산한 경로와 현재 관측만 사용한다. 기록된 미래 정답은 제어 입력이 아니다.
- 정지 거리가 부족하면 `REFERENCE_INFEASIBLE`, 정지 요구에 거리가 없으면
  `STOP_DISTANCE_UNKNOWN`을 표시한다. 편안하게 정지 가능하다고 꾸미지 않는다.
- 다음 위치를 가속으로 고정 가정하는 오류를 수정하고, 한 주기 안에 정지하는 경우의 이동
  거리를 별도로 계산했다. 초기 실패 결과는 `scenario_matrix_v1`에 보존했다.
- `research_agent_reference_adapter.py`: 모의 agent에만 시험한 비활성 연결 경계다. 공용
  BasicAgent/수집기에 연결하지 않았다. throttle/brake/steer를 변경하지 않는다.
- 외부 긴급 제동 명령이 주어지면 그대로 반환한다. 긴급 상태만 있고 명령이 없으면 정상 agent를
  호출하지 않고 owner의 fail-safe 처리를 요구한다. `control=None`을 계속 주행으로 해석하면 안 된다.
- 기존 agent가 내부적으로 발견한 위험 때문에 반환한 brake도 약화시키지 않는다.

## 3. 오프라인 검증 결과

- 신규 및 기존 runtime/goal-stop 회귀: **203개 통과**. 초기 201개 결과도 보존했다.
- 두 TRAIN 경로 × 주기 4종 × 횡가속 목표 3종 × 가감속 목표 3종: **72/72 통과**.
- 최초 72개 중 8개 실패는 0.2초 주기의 종점 내부 정지 적분 문제였다. 수정 후 전부 통과했다.
- 추가 정지 거리/긴급 상태 조합 20개에서 늦은 정지를 정상으로 승인하거나 긴급 명령을 완화하지 않았다.
- 별도 seed 20260922의 무작위 경로·주기·가감속 조건 **1,000/1,000개**도 이상적 계산을 통과했다.
  최종 소스 기준 재실행 `artifacts/training/2026-09-22/offline_turn_envelope_n_v1/stress_v2.json`,
  CPU 단일 프로세스·nice 19, 실제 계산 시간 약 16.4초다. 실제 시뮬레이터 주행 1,000회가 아니다.
- 실제 기록 관측 재생에서는 Town01 903개 중 참조 가능 709·불가능 194, Town07 315개 중
  가능 7·불가능 308이었다. 기존 고속 관측값이 보수적인 참조를 이미 벗어난 경우를 표시한 것이다.

**72개 통과는 이상적인 운동 계산의 논리 검사다. CARLA 주행·센서·조향·충돌·학습 모델의 성능
시험이 아니다.** 참조를 적용한 차량 반응은 미측정이며, replay의 가능 비율도 주행 성공률이 아니다.

## 4. 기존 K1 TRAIN의 물리 타깃 정합성을 전수 비교했다

명시적으로 선택한 TRAIN episode와 표본 hash를 검증하고 기존 runtime gate에 정답 XY/속도를
넣었다. DEV/TEST episode payload는 열지 않았고 새 데이터 필터나 라벨 수정도 하지 않았다.

| 원본 구간 | 전체 | 현재 runtime 타깃 검사 통과 |
| --- | ---: | ---: |
| 기존 Town07 직진 | 309 | 103 |
| 기존 C-track 좌회전 | 304 | 131 |
| 기존 Town01 우회전 | 534 | 251 |
| 추가된 이동 직진 5 episode | 1,640 | 1,640 |
| 합계 | **2,787** | **2,125** |

실패는 662개다. runtime 통과가 물리 decoder의 완전한 표현 가능성까지 보장하지는 않는다.
추가 이동 직진은 정합성이 좋은 반면 기존 회전/급가감속에 충돌이 남아 있다는 비교 근거다.
이 비교만으로 K1의 직진 개선이나 우회전 퇴행의 인과관계를 완전히 증명하지는 않는다.

특히 기존 Town01 우회전 534개를 정답으로 진단 분류하면 다음과 같다.

| 진단 분류 | 전체 | 통과 |
| --- | ---: | ---: |
| 미래 최고 속도 0.5m/s 미만 | 120 | 118 |
| 움직이며 미래 yaw 최대 절댓값 15도 미만 | 342 | 133 |
| 움직이며 미래 yaw 최대 절댓값 15도 이상 | **72** | **0** |

분류는 분석용 미래 라벨을 사용하며 추론 입력·학습 선택기로 사용하지 않았다. 회전 72개의 첫
실패는 횡가속도 50개, 곡률 22개다. 그중 11개는 첫 미래 지점에서, 61개는 이후 지점에서 발생했다.
곡률 실패 시점의 속도는 약 0.336–0.549m/s, implied curvature는 약 0.611–0.678rad/m였다.
횡가속도 실패는 약 7.77–8.31m/s의 구간을 포함한다. 따라서 단순히 모든 실패가 고속 때문이라고
단정할 수 없으며 **저속 위치/heading 표현과 고속 회전 속도 계획을 분리해 개선**해야 한다.

첫 실패의 수치는 복제한 검사 공식이 아니라 변경하지 않은 runtime 함수의 예외 시점에서
허용된 숫자 변수만 읽었다. 이전 threshold를 변경하거나 실패 표본을 제거하지 않았다.

### 겹치는 미래 구간을 원본 시간으로 대응한 후속 결과

72개 실패 window의 첫 실패 시점은 **13개 native 프레임**으로 모였다. 곡률 실패 22개는
native frame 26709에 21개, 26711에 1개가 대응했다. 따라서 72개를 독립 주행 실패 72회나
22개를 별도 물리 사건 22개로 표현해서는 안 된다.

첫 곡률 실패 근방은 brake 0.5에서 throttle 0.75로 재출발하는 구간이었다. 낮은 속도에서
센티미터 단위 chord 방향 변동이 큰 곡률로 계산됐다. 기록된 yaw-rate/speed와
tan(steering)/wheelbase는 서로 다른 정의의 참고값이며 gate의 chord 곡률을 대신하지 않는다.
구형 수집에는 raw actor snapshot과 acknowledged receipt가 없어 시뮬레이터·표현·샘플링 중
정확한 원인을 완전히 분리할 수 없다. 이를 데이터 삭제나 gate 완화로 처리하지 않았다.

## 전체 목표·다음 실행 순서

전체 9영역·30기능, 부분 근거 10/30, 자체 모델 폐루프 승인 0/30은 그대로다. 현재는 직진·회전·
종점 정지·속도 추종의 기반 정합성 복구 단계다. 이번 새 학습 0회, 새 CARLA 수집 0회다.

1. 저속 곡률 오류가 위치-속도 경계·heading 정의·실제 조향 중 어디에서 발생하는지 원본 native와 대조.
2. 실수집 전 신호 상태/정지 거리·reference/실제 속도·상위 긴급 명령 여부를 별도 로그로 남길 통합 준비.
3. 다른 테스트의 자원 범위 확인 후 소유권·runtime lock·포트·GPU를 다시 확인하고 전용 수집만 실행.
4. 정지/회전 target 품질과 독립 경로 범위를 만족한 데이터를 만들고, 기존 K1 구조의 고정 예산
   비교 학습을 수행. 기존 실패 표본 삭제만으로 우회전 학습이 해결됐다고 보지 않는다.

속도 참조만으로 제동 응답·신호 대응·저속 곡률이 해결된 것은 아니다. 실수집 이후 품질을 다시
측정해야 하며 그 전에는 추가 학습 시간을 써도 성능 회복을 보장할 수 없다.
