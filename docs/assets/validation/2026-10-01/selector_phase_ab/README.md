# 주행 선택기만 학습해도 정지 문제는 남았다

<!-- HH_261001 - Keep the failed frozen-generator pair and its next evidence-led investigation readable. -->

**결론: S0와 S1 모두 채택하지 않는다.** 기존 AH의 궤적 생성부를 그대로 두고 선택기만 보정했지만, 같은 CARLA 시험에서 두 모델 모두 약 4.2m 뒤 멈췄다. ‘움직이는 후보가 있는데 잘못 고른다’는 관찰은 맞지만, 이번 비중 조정만으로 해결되지는 않았다.

## 무엇을 실제 학습했나

PRO6000 GPU 0에서 원래 AH의 영상 처리·상태 처리·궤적 생성·정규화는 모두 고정했다. 기존 선택기 가중치 **3,084개만** 학습했다. TRAIN 2,787개의 고정 특징/후보를 한 번 계산해 재사용했으므로 optimizer 자체는 두 팔 합계 약 **9.7초**였고, 전체 데이터 확인·특징 계산·최종 평가는 별도다. 전체 모델을 9.7초 만에 다시 학습한 것이 아니다.

두 모델은 각각 3,000 step·12,000회 표본 노출, 동일 순서로 모든 2,787개 표본을 최소 4번 보았다. S0는 원래 표본별 평균, S1은 출발·정지·저속·이동의 비중을 보정했다. 두 최종 가중치가 저장된 후에만 같은 DEV를 평가했다. 원래 AH와 새 두 모델의 선택기 외 모든 텐서가 바이트 단위로 동일함을 export 때도 다시 확인했다.

| 확인 항목 | S0 | S1 |
| --- | ---: | ---: |
| TRAIN 저속 즉시 출발의 정답 후보 일치 | 6/18 | 6/18 |
| 실제 20초 주행 진행 거리 | 4.22m | 4.26m |
| 마지막 정지 구간 | 15.85초 | 15.85초 |
| 충돌 / 차선 센서 이벤트 | 0 / 0 | 0 / 0 |

| 새 기능 승인 | 0 | 0 |

각각 같은 Town07 TRAIN 경로·9km/h 상한·10Hz·동일 추종기로 실행했다. 초기 전문가 출발 명령 11개 이후 모델 제어 366개가 ACK를 받았다. 목표 도달, 차체 전체 차로 포함, 독립 맵 일반화 검증은 아니다.

두 실행 모두 즉시 포트 독점 바인드 검사에서 TIME-WAIT와 함께 `Err98`이 나왔다. 원래 `OWNER_FAILURE`는 그대로 두고, 후속 독립 검사에서 소유 PID/그룹 소멸·모든 포트 바인드·62개 소스와 8개 입력 해시 일치를 확인했다. 주행 실패를 인프라 오류 탓으로 바꾸지 않는다.

## 바로 이어지는 조사

기존 TRAIN의 정지 대기와 출발 입력은 매우 비슷하지만 완전히 같은 바이트는 아니었다. 후속 [실제 제어 인계 입력 감사](stationary_context_live_handoff.json)에서 **S1은 과거 Town07 출발 당시 조향 이력을 정확히 재현했다**. 따라서 초기 조향 차이를 이번 정지의 원인이라고 할 수 없다. AH·S0·S1 모두 처음에는 움직이는 후보 5를 선택해 출발했으며, S0/S1은 약 0.9초 뒤 약 2.04m/s에서 후보 1로 바뀌고 이후 멈췄다. 문제는 초기 출발 자체보다는 출발 후 정지 성향 예측으로 되돌아가는 것이다. 입력 영상·경로까지 바이트가 동일하다는 주장은 하지 않는다.

다음 검증 대상은 **수집 준비를 위한 강제 대기 시간이 주행 정답으로 학습되는 영향**이다. 입력에는 대기 타이머가 없는데, 정지 상태가 거의 같은 동안 “몇 초 뒤 출발할지”라는 정답만 달라진다. 해당 원본·이력은 보존하고, 대기 anchor의 학습 포함 여부만 바꾸는 비교를 준비한다. 이것이 유일한 원인이거나 수정 후 주행이 해결된다고 미리 단정하지 않는다.

동시에 전문가 데이터의 실제 출발·정지 품질을 개선한다. 새 Town07 수집은 초기 10Hz 미래 궤적 22개가 모두 운동 한계를 통과했지만, 20Hz 출발 가속도 1회 위반과 종점 정지 실패가 있어 아직 학습에 편입하지 않았다.
