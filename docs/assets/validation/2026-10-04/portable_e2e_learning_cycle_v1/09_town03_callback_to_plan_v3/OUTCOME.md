# 영상 원본 연결은 해결, 100ms 지연은 아직 미달

<!-- HH_261004 - Keep the complete actual v3 failure and distinguish source-identity repair from real-time driving approval. -->

로컬 CARLA에서 같은 **GOOD6000·CPU4/1·PI 2.4m/s·preview 0.5초**로 전체 45초를 실행했습니다. 현재 실행은 종료됐고 소유 서버 정리·포트 해제·소스 동일성을 확인했습니다.

이번에 해결된 것은 **계측의 원본 영상 연결**입니다. 같은 프레임 번호가 반복돼도 실제 사용한 영상 객체·센서·시각·픽셀 SHA를 정확히 연결했습니다. 900개 차량 상태·450개 6카메라 묶음·904개 ACK·415회 새 모델 계산과 **7,200개 처리 경계 시각**을 모두 검증했습니다. 이전 v1/v2 FAIL은 그대로 남겼습니다.

| 실제 확인 항목 | 결과 |
| --- | --- |
| 차량 중심 오차 | p95 **3.04cm**, 최대 **3.08cm** |
| 기존 차체·속도·명령 전달 검사 | 통과 |
| 정확한 영상 원본·5묶음 과거 입력 연결 | 통과 |

| 벽시계에서 관측한 계획 생성률 | **8.47Hz** — 10Hz 보장이 아님 |

**종합 FAIL입니다.** 차량이 잘 직진했다는 것과 제때 다음 계획을 내는 것은 별개입니다. 전체 경로 목표점·독립 TEST·정식 반복 평가·Autoware 어댑터도 아직 남아 있습니다. 정식 완료는 **메인 0/9·하위 0/30** 그대로입니다.

## 왜 늦었는가, 무엇을 바꿀 것인가?

최악 프레임에서 마지막 카메라 callback의 queue 전달은 약 11µs, 이후 SHA는 약 0.4ms였습니다. 그런데 원래 queue를 읽기 시작하기까지 약 **44.21ms**가 더 걸렸습니다. 실제 queue 대기는 그 뒤 약 **0.026ms**뿐이었습니다. 모델 계산은 해당 프레임 약 29.10ms였습니다.

따라서 이 프레임은 카메라 Hz나 모델 계산 하나만으로 설명할 수 없습니다. 원래 영상 묶음 함수 앞의 wrapper를 조사합니다. 매 묶음마다 저장 폴더 전체를 재귀 순회하는 용량 보호 코드가 있어, **동일한 전체 파일·심볼릭 링크·용량 검사를 유지하면서 순회 비용만 줄이는 새 구현**을 비교할 예정입니다. 이번 기록만으로 그 코드가 지연의 확정 원인이라고 주장하지 않습니다. 안전 검사를 제거하거나 100ms 기준을 늘리지 않습니다.

동시에 준비한 종점 수치 수정은 실제 전체 209m 경로에서 별도 검증합니다. 모델 곡률·원래 선호 속도는 유지하고, 종점 내비게이션 감속 개입을 명시합니다. 교사가 정차한 결과나 미학습 STOP head를 모델 정차 성공으로 세지 않습니다.
