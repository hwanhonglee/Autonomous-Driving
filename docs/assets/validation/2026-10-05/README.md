## 실행 지연 개선에서 제외한 가설

**12:20 KST 확인:** 새 카메라 해시 캐시의 모의 검사 32개는 통과했지만 속도 개선으로 채택하지 않는다. 실제 V5는 이미 입력을 변경 불가능한 bytes에 복사하고 해시를 재사용한다. 전체883회 fresh 추론에서 새 해시6·재사용60·mutable 우회0·보존60이었다. 첫 prefill에서만 새60개를 계산하고 나머지22개 prefill도 새6개다. 재사용60에는 먼저 입장시킨 새6개도 포함한다. 입력 복사 평균은 약0.574ms, 기존 build/원본·정규화 텐서 해시를 포함한 묶음은 평균26.782ms였다. 묶음의 시간으로 내부 각 단계의 원인별 시간을 만들어내지 않는다.

따라서 일부러 매번 재계산하는 느린 대조군을 만든 뒤 “가속”이라 부르는 실험은 하지 않았다. 새 후보의 실제 NN 벤치마크·라이브 적용은 **0회**다. 다음 우선순위는 원래 입력·가중치·안전 검사를 유지한 GPU CNN 추론과 전체 실제 주행 주기의 검증이다. 현재는 그 실행에 필요한 추가 공간의 승인 문제가 남았다.

## 그 다음 학습은 무엇을 바꿀 것인가

제안 순서는 **기존 GOOD6000에서 속도 부분만 학습 → 공통 특징·속도를 고정하고 경로 보정만 학습**이다. 새 기능 head를 붙이는 것이 아니다. 실제 TRAIN의 속도·곡률·미래 경로 정답이 주 목표이고, 기존 GOOD의 같은 TRAIN 입력 출력은 퇴행을 막는 보조 목표로 검토한다. HOLDOUT·known-DEV·TEST를 학습 손실에 넣지 않는다. 기존 모델의 미달까지 영구 고정하지 않도록 보조 손실의 계수와 단계 예산은 실행 전에 선언해야 한다.

속도가 달라지면 같은 곡률에서도 시간별 위치가 달라지고, 곡률이 달라지면 횡가속 제한을 통해 속도도 달라진다. 따라서 이 분리 설계만으로 전체 경로 보존을 보장할 수 없다. 새 동결 범위·부모 GOOD·export/loader 계약과 동일 조건의 비교가 필요하다. 오늘 COMMON에서 학습한3개를 GOOD 시작 후보의 동일 조건 대조군으로 재사용하지 않는다. **직진의 실행 지연 검증을 먼저 진행하고**, 그 뒤 이 설계의 효과를 TRAIN·독립 평가·실제 주행에서 확인한다.

## 다음 순서

1. 새 3개 모델의 개선·퇴행 수치를 읽기 쉬운 표로 확인한다. 모든 실패를 남기고 사후 기준을 낮추지 않는다.
2. 실제 기존 코드보다 나아질 근거가 있는 지연 개선만 동일 가중치·동일 입력 A/B로 측정한다. 중복 해시 캐시 가설은 제외했다. 기록된 JPEG에서 만든 BGRA 비교라면 원래 실시간 BGRA의 성공으로 부르지 않는다.
3. 추가 정리가 승인되고 필요한 공간을 확보하면 출력 동등성·실제 전체 주행 주기를 확인한다. 동일 모델을 GPU로 실행하는 준비도 이 단계에 포함한다.
4. 실제 모델이 조향·주행을 담당하는 직진을 재시험한 뒤, 독립 장소·날씨·seed·원래 반복 분모로 기능을 검증한다. 교사 주행이나 한 번의 짧은 직진을 완료로 세지 않는다.
5. 첫 기본 주행을 안정화한 뒤 회전·종점 정지·속도 추종을 이어간다. 지도 인식·자동 생성은 별도 모델·별도 판정으로 진행한다.

실제 5모델 평가는 **11:20:23~12:06:13 KST**였다. 다음 CPU 입력 비교와 실제 주행 전체의 완료 시간은 아직 계측하지 않았다. 크레딧 잔액·정확한 미래 토큰 비용·기능 완료 날짜는 이 환경에서 확인할 수 없다.

추가 컴파일 캐시 정리가 승인되면 약1.80GB를 PRO6000 개인 폴더에 백업·검증한 뒤 정리하는 절차가 필요하다. 기존 `.o` 승인만으로 캐시까지 삭제하지 않는다. 이 정리는 GPU 준비 예약을 충족할 가능성이 있지만, 실제 실행 직전 가용 공간·다른 작업·소유권을 다시 확인해야 한다. 이후 반복 주행의 저장 예산은 별도다.
